# 평가·완료 기준

## 세 가지 다른 통과

문서 정합성 통과는 원장과 링크가 맞는다는 뜻입니다. 제품 합성 평가 통과는 정해진 인공 사례에 맞게 동작한다는 뜻입니다. 실제 게임 검증은 특정 설치본·환경에서 확인했다는 뜻입니다. 앞 단계를 뒷 단계의 증거로 사용하지 않습니다.

평가 원장은 [evals.jsonl](../harness/evals.jsonl)입니다. 초기에는 모든 항목이 not_run이고 fixture 이름은 앞으로 구현할 시나리오 식별자입니다. 입력·정답·상태·근거를 분리합니다. Task의 eval_ids는 어떤 평가를 통과해야 완료되는지 지정합니다.

## 계량 기준

| 지표 | 정의 | v0.1 기준 |
|---|---|---|
| 인용 정확성 | 제시한 span이 해당 사실·필드를 포함하는 비율 | 필수 합성 사례 100% |
| exact 검색 | 이름/ID exact 질의에서 정답이 첫 결과인 비율 | exact 합성 사례 100% |
| recall@5 | 답이 있는 질의 중 top 5에 정답이 포함된 비율 | 검색 corpus 95% 이상 |
| 올바른 보류 | 미지원/미확인 사례에서 단정하지 않은 비율 | 안전 필수 사례 100% |
| snapshot 누출 | 다른 문맥의 데이터가 섞인 건수 | 0 |
| 부작용 | 원본 쓰기·무단 네트워크·경로 탈출 건수 | 0 |
| 복구 | 중단/실패 후 이전 active snapshot이 유지되는지 | 필수 사례 전부 |

검색 corpus는 이름·ID·두 글자 한국어·표기 정규화·동명 충돌·없는 질의를 균형 있게 포함하고 최소 40질의를 목표로 TASK-018에서 고정합니다. 정답 없는 질의는 recall 분모에서 제외하되 별도 오답률을 평가합니다. easy 사례만 늘려 기준을 맞추지 않습니다.

성능은 10,000개 합성 엔티티에서 warm query p95 500ms를 초기 목표로 측정합니다. CPU·RAM·OS·Python·SQLite·corpus hash·반복 횟수·cold/warm 구분과 원시 시간을 기록합니다. 측정 전 보장하지 않으며 CI의 절대 시간 hard gate는 기준선과 변동폭을 확인한 뒤 결정합니다.

## 결과 형식

각 실행 기록에는 task/eval ID, 제품 commit, 문서/fixture 버전, OS·runtime, 실행 명령, 시작/종료 시각, exit code, pass/fail/blocked, 기대와 실제, 제한, evidence 경로가 필요합니다. 전체 로그에 개인 원문을 넣지 않습니다. 저장소 공개 가능한 결과는 harness/evidence/ 아래에 두며 비공개 결과는 비식별 요약과 위치 설명만 남깁니다.

상태를 pass로 바꾸려면 실제 실행 evidence가 있어야 합니다. 과거 pass를 재사용하려면 동일한 코드·fixture·환경 조건임을 설명해야 합니다. 기본은 변경 영향 평가를 다시 실행합니다. 제품 코드가 없거나 fixture가 아직 없으면 not_run입니다.

## 검토

개발자는 실패 재현과 결과를 제출하고 검토자는 수용 조건·근거·부정 사례를 확인합니다. 독립 검토가 없으면 self_review라고 표시하며 타인 검토를 지어내지 않습니다. 모델 답변 품질은 문장 유사도보다 사실·인용·보류를 평가합니다. 모델 스스로 매긴 점수만으로 F-016을 승인하지 않습니다.

## 릴리스 판단

preview는 합성 게이트와 안전 기준 통과 후 가능합니다. 실제 사용자 설치본 검증이 없으면 validated v0.1로 부르지 않습니다. 실패·blocked·not_run이 남아 있는데 '전체 검증 완료'라고 요약하지 않습니다. 게임 호환성은 검증한 snapshot과 범주에 한정합니다.
